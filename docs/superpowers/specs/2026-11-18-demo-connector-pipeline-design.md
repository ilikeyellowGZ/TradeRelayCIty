# TradeRelayCity remote access and demo connector design

Date: 2026-11-18

## Scope and delivery order

1. Verify owner authentication on a dedicated Cloudflare staging Worker and D1 database. The staging Worker must keep simulation routes disabled, accept only the existing username/password auth paths, protect `/app` on the Worker, and prove sign-in, rejection, session lookup, sign-out, and expiry behavior over HTTPS.
2. Pair one Windows connector to the authenticated owner with a short-lived, single-use code. Store only a digest of the device credential in D1. The connector stores its credential in Windows Credential Manager. The owner can list and revoke devices. All connector requests are authenticated independently of browser sessions.
3. Read MT5 account identity, balance, equity, and open positions through the terminal's loopback MCP endpoint and upload a bounded, normalized snapshot over HTTPS. The Worker binds the first reported demo account identity to the paired device and rejects account switches until the owner explicitly re-pairs. The dashboard shows snapshot age and never labels stale data as live.
4. Add a demo-only command ledger, risk gate, and connector execution state machine. The Worker may queue a BUY or SELL only from a bounded strategy candidate, a valid AI opinion, and deterministic risk approval based on a fresh broker snapshot and verified symbol contract. The connector persists intent before calling MT5. An uncertain submission is reconciled against broker orders and deals before any retry. No live-account order path is enabled.

## Boundaries

- The browser holds only an HttpOnly owner session and can create/revoke pairing codes or inspect its own accounts. It never receives MT5 or device secrets.
- The connector makes outbound HTTPS requests to the Worker and uses a loopback-only MT5 MCP endpoint. A device credential is scoped to one owner and one broker account identity. Revocation takes effect at the next request.
- D1 is the command and snapshot ledger. MT5 is authoritative for actual balance, positions, orders, and deals. A Worker request never directly calls a local terminal.
- Separate staging resources prevent remote login validation from activating broker execution. The production `wrangler.jsonc` placeholder remains until the owner chooses production settings.
- Entry execution is demo-only and opt-in. An unknown account type, missing contract field, missing MCP tool/schema, stale snapshot, closed market, exceeded risk limit, missing protective stop, or unknown prior submission denies an entry. The existing `LIVE_ENTRY_EXECUTION_ENABLED = False` remains.

## Pairing and snapshot contract

- The owner creates a random pairing code with a 10-minute expiry. D1 stores its digest, owner ID, expiry, and consumption timestamp. The code is shown once. The exchange endpoint permits a limited number of attempts per code/IP window and consumes the code atomically.
- On successful exchange the Worker creates a 256-bit random device token, stores its SHA-256 digest, and returns the plaintext once. Connector storage has no plaintext-file fallback.
- Snapshot upload requires `Authorization: Bearer <device token>`, a matching device, and a bounded JSON body. The connector includes broker, server, login, account type, currency, balance, equity, observed UTC time, and bounded open positions. The Worker validates types and sizes before persisting a single latest snapshot and normalized position rows.
- The first valid DEMO snapshot establishes account binding. Later snapshots must match broker, server, and login exactly. A LIVE or unknown account is read-only and never execution eligible.
- Browser reads require the owner session and owner-scoped SQL. Connector writes require the device token and device-scoped SQL. Mutation endpoints check same-origin browser requests; connector endpoints use bearer auth instead of browser cookies.

## Demo execution contract

- Command IDs and idempotency keys are generated by the Worker. A claim has a short lease and monotonically increasing fence. Expired or revoked devices cannot claim. The command contains exact account binding, symbol, side, volume, stop, target, and expiry.
- The connector re-reads account identity, contract, quote, open risk, and recent broker history immediately before submission. It runs the deterministic risk check again and records the intent in SQLite before a single order call.
- An order timeout or ambiguous result sets `unknown` and blocks replay. Reconciliation searches broker orders/deals by command reference and account binding. Only a confirmed absence under a validated broker query may permit a controlled retry; otherwise the command stays unknown for review.
- The Worker records broker references and final state only from the paired device. Duplicate acknowledgements are idempotent. The dashboard can stop new entries immediately; revocation prevents further claims.
- Until a real demo terminal reveals exact MCP input and output schemas, order calls remain gated. Tests use a fake broker with success, reject, partial fill, timeout, and duplicate cases. A real demo order is a separate validation step after capability inspection and account identity confirmation.

## Verification

- Automated tests cover auth gates, pairing expiry/replay/revocation, cross-owner access, snapshot validation and binding, stale data, lease/fence behavior, risk denial, crash recovery, and unknown-result reconciliation.
- Staging HTTPS smoke verifies owner sign-in/session/sign-out and denied simulation routes. Read-only MT5 verification checks exact account identity and tool schemas without calling a trade tool.
- Demo execution validation uses the user's demo terminal, a minimal allowed volume, broker-side stop, a known symbol contract, and broker history reconciliation. No live-account execution test is authorized by this design.
